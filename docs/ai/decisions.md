# AI Agent Decisions

- Desktop app release parsing in `app/utils/server/github.ts` intentionally uses a hardcoded allowlist of expected GitHub asset names. `.zip` assets are treated as portable packages for every platform, while `.dmg`, `.deb`, and `.exe` are installer packages.
- The `/download` page groups desktop app release files by platform and architecture, then renders installer and portable package buttons inside the same group. Recommended desktop app highlighting is based on `ua-parser-js`, with client-side feature checks used after mount to refine CPU architecture when the browser supports it. Mobile, tablet, and wearable devices do not get a highlighted desktop recommendation.
- `UiBurger` treats the numeric `size` prop as the burger line width in pixels. Line height, gap, and active-state translate distance scale from that width via CSS variables, preserving the original 12px-wide visual proportions by default.
- `UiRange` keeps its custom fill and thumb as decorative container pseudo-elements. Those pseudo-elements must not receive pointer events, because Firefox can otherwise start drag on the decoration instead of the native `input[type='range']`.
- Airport counter horizontal placement is based on cached measured ICAO label width plus counter declutter overflow and a gap. The cache key must include both ICAO and the `localsLength > 3` layout branch, and popup offset should use the shared counter popup offset helper so the OpenLayers counter and HTML popup stay aligned.
- Airport labels are anchored around the airport coordinate with `textBaseline: 'middle'`: ICAO is centered on the coordinate unless the unstaffed point is shown, in which case the point is centered on the coordinate and ICAO is one label line above it. Airport counters use the same centered baseline for their fake declutter obstacle, icon row, and text row so multi-counter stacks stay vertically centered against that anchor.
- Settings page hash navigation scrolls the internal `.settings_content` container, so target offsets must be calculated relative to that container's bounding rect and `scrollTop`, not relative to the viewport top.
- V1-to-V2 settings migration preserves only settings with a V2 equivalent and groups mappings first by source object (`userSettings`, `localSettings`, `mapSettings`), then by V2 section inside each source. Old negative keys such as `disableNavigraph`, `disableQueryUpdate`, and `hideTaxiways` are migrated into positive V2 keys by inverting their boolean values. Legacy named colors are converted to V2 color names through `legacyColorsList` coverage, while explicit hex/rgb colors remain unchanged. Migrated transparency values are rounded to two decimal places before V2 validation. Removed keys such as Navigraph `gatesFallback`, SIGMET `activeDate`, airport `aircraftHoverDelay`, and local map position/zoom remain unmigrated.
- `ViewMap` owns only the default OpenLayers interactions and the distance starter interaction. It must remove only those managed interactions when distance settings change, because `MapSelect` and `MapDistance` add their own interactions later and will not re-register them after a blanket clear. The distance tool starts from OpenLayers `dblclick`/CTRL pointer events, not by manually timing two `pointerdown` events.
- On touch devices, the distance tool always starts only from OpenLayers `dblclick`, irrespective of a desktop-saved CTRL+Click preference. Single taps must continue to reach map selection, and double-tap zoom remains disabled while the ruler is enabled.
- Map render hot paths should avoid rebuilding reactive arrays or doing `Array.includes` per OpenLayers feature. Keep `renderedAirports`/`renderedPilots` assignments stable when declutter output has not changed, and use per-render `Set` lookups for visible airport/pilot membership checks.
- `ViewMap` must dispose its OpenLayers `Map` on component teardown after child map layers unmount. Route changes and settings preview iframes can create fresh map instances, so `postrender`/move listeners, DOM listeners, resize observers, map target, and rendered feature snapshots must be cleaned to avoid accumulated render loops and FPS degradation.
- InfluxDB 3 uses `@influxdata/influxdb3-client`, SQL queries, and V3 line protocol writes. Keep `INFLUX_BUCKET_MAIN` and `INFLUX_BUCKET_PLANS` as environment names for the two InfluxDB 3 database names to minimize app config churn, but treat them as databases in code and setup scripts.
- InfluxDB 3 Core storage is not mounted onto the old InfluxDB 2 data path. Runtime data defaults to `/tmp/influxdb3` because the official image runs as a non-root user; Kubernetes uses a separate `radar-influx-v3` PVC mounted there with pod `fsGroup`. Historical InfluxDB 2 data requires a separate export/import migration if it must be preserved.
- InfluxDB 3 Core admin token files for the official image contain JSON with a `token` field. `INFLUX_TOKEN` used by the Influx image must be an InfluxDB 3 token starting with `apiv3_`.
- VATGlasses client updates must not replace existing active positions with an empty result when live controllers still match VATGlasses positions but no airspace matches in the current tick. They also must not replace an online position's previous sectors with an empty sector list from a transient runway/ownership recalculation. Treat these as transient data inconsistencies and keep the previous geometry while still marking those controllers as handled by VATGlasses.
- VATGlasses level filtering must treat non-finite `localSettings.vatglassesLevel` as invalid and fall back to a finite default. `NaN ?? 999` still produces `NaN`, causing every non-combined sector min/max comparison to fail and the layer to render zero sectors.
- Non-combined VATGlasses sectors are filtered before OpenLayers features are created, so changing `vatglassesLevel` must rebuild the sector feature list. Calling `vectorSource.changed()` only restyles old-level features and can make sectors disappear until the next full data update.
- Aircraft straight-track feature matching must use the same transparency-adjusted color stored on the feature. Comparing an opaque status color to a stored `rgba(...)` color makes existing straight tracks miss updates when turns transparency is enabled.
- `DashboardEditPopup` keeps editable state in one `reactive<DashboardPayload>` object. The payload factory normalizes persisted optional fields for editing, while UI color adapters convert directly at the component boundary without separate form state.
- Dashboard traffic-prediction options are stored in `DashboardSettings.predictedWindow`. The chart takes these as its baseline and persists only per-link overrides in route query parameters, so shared links reproduce the displayed forecast settings without cookies.
- Dashboard map aircraft mode is stored in `DashboardSettings.aircraftMode`; the `aircraft` page-query override takes precedence and is forwarded to the iframe as `airportMode`. Multi-airport dashboard maps apply that mode while assembling their visible-aircraft set.
- Enroute dashboard results always exclude pilots identified as on-ground by airport traffic data, even without an FL band. Sector polygon membership alone is not sufficient to classify a pilot as enroute.
- Navigraph enroute rendering caches each pilot's static feature keys. On every update it selects the next waypoint using the same distance, heading, and altitude rules as the full pass; when that selected waypoint and the route settings are unchanged, retain the keys in the global cleanup `Set` and update only the aircraft-to-waypoint line. A route or target change must run the full rebuild so SID/STAR and stale-feature cleanup remain correct.
- VATSpy boundary GeoJSON is stored in IndexedDB by `fir.boundary`, never in the in-memory VATSpy metadata object. A VATSpy version change must atomically replace both metadata and boundary records. The map renders offline boundaries once into OpenLayers and releases their GeoJSON snapshot; online ATC and dashboard enroute lookup load only the needed boundary record from IndexedDB.
- Dashboard traffic-prediction query overrides apply only when their route query value is present as a string. Missing query keys must preserve dashboard/default `predictedWindow` values, because thresholds allow `0` as an explicit disable value and `stacked` defaults may be `true`.
- Stacked dashboard traffic-prediction columns keep airport colors as their fill, so caution/alert threshold states are shown through bar borders. Border threshold checks must include both warning and alert thresholds, with `0` disabling each threshold.
- Aircraft map features use an invisible square `RegularShape` style for hit detection, with side length equal to the rendered icon's larger dimension. Keep this aircraft-only so global map `hitTolerance` and other feature click priorities stay unchanged. Aircraft rendering intentionally uses PNG for regular default/ground non-list aircraft, and SVG for hover/active/list coloring because SVG recoloring is more reliable for those states. Aircraft `_ipx` PNG requests must account for `devicePixelRatio`, capped at 3x, so small rendered icons do not upscale low-resolution bitmaps on Retina displays.
- Aircraft hitbox styles must be cached per rendered hitbox size instead of mutating one shared OpenLayers `Style`. The hitbox layer was added after 2.0.0-beta.4 and should stay isolated from the already-working aircraft image/text style flow to avoid stale or stuck aircraft icons.
- Tile-backed map layers must clear their source and call `dispose()` when unmounted, not only remove themselves from the map. Heap snapshots showed disposed OpenLayers `Map` instances can otherwise retain undisposed vector tile layers and `VectorTile.features_` flat coordinate arrays.
- Smooth aircraft movement delay is based on the cadence of accepted mandatory-data snapshots, not on the fraction of pilots whose coordinates changed. Many pilots can be stationary on the ground, so a moved-pilot percentage threshold underestimates the real data interval and causes extrapolate/freeze/catch-up jumps between VATSIM snapshots.
- Smooth aircraft movement intentionally uses linear interpolation plus unbounded dead-reckoning from the latest sample for moving aircraft. Extrapolation must use reported `groundspeed` and `heading`, not coordinate delta between samples, because VATSIM/mandatory position jumps can imply a false speed. Do not reintroduce Hermite/PCHIP easing or short extrapolation caps unless there is a separate correction strategy, because easing changes apparent speed and caps make aircraft stop before the next VATSIM snapshot.
- Mandatory aircraft data has no per-pilot update timestamp. When a pilot appears in a newer mandatory snapshot with unchanged coordinates, treat it as "no fresh sample for this pilot" and keep dead-reckoning from the last movement vector rather than inserting a zero-speed sample. Smooth geometry updates are capped to 30 FPS and new-sample corrections are blended to reduce visible wobble.
- With smooth aircraft movement enabled, dynamic aircraft scale must be based on the feature's current smoothed geometry, not the raw mandatory snapshot coordinates. The smooth RAF loop also updates aircraft `coordinates` and `scale` properties together with geometry so popups, hitboxes, labels, and icon sizing stay aligned.
- Smooth aircraft movement must keep aircraft-dependent lines in sync with the smoothed position. The RAF loop updates existing departure straight lines, the current tail segment, and the current Navigraph `enroute-${callsign}` segment directly. It may update `navigraphWaypoints[cid].coordinates` for state consistency, but must not `triggerRef` from the RAF loop because that causes `NavigraphRoute` to redraw from its cache and makes the live next-waypoint line jump backward/forward. Do not update `arrival-straight` from the RAF loop while `updateAircraftTracksData()` owns rebuilding that geometry, because two competing `setGeometry()` calls make the arrival line jump.
- Aircraft track/route builders must receive the feature's current smoothed coordinates when smooth movement is enabled. Passing raw mandatory snapshot coordinates into `updateAircraftTracksData()` makes arrival/departure lines rebuild from the old point on each render update, causing visible backward jumps before the RAF loop catches up.
- Aircraft turns (`/api/data/vatsim/pilot/:cid/turns`) must not be requested more often than once every 15 seconds per aircraft. Smooth movement updates the current tail/route line locally between server refreshes; if a full turns refresh is needed, mark it pending and wait for the same per-aircraft interval instead of issuing a second immediate request.
- Smooth aircraft movement is suspended when `renderedPilots.length` exceeds `map.preferences.aircraft.showLimit`. The same load gate must be used by both the RAF loop and `setMapAircraft()` so high-density views fall back to normal snapshot updates instead of freezing aircraft in their last smoothed positions.
- Smooth movement uses separate extrapolation thresholds for airborne and ground aircraft. Keep airborne at a conservative threshold, but use a low ground threshold so taxiing aircraft under 30 kt continue dead-reckoning instead of moving between samples and stopping after every latest sample.
- Any aircraft line geometry that is rebuilt both by `updateAircraftTracksData()` and the smooth RAF loop must use identical `greatCircle` options. In particular, `departure-straight` uses `npoints: 8` in both paths; otherwise the same endpoints produce different intermediate coordinates and the line appears to jump.
- Kafka worker health logging is aggregated in `app/utils/server/worker/kafka.ts` on a 5s window. Keep it windowed instead of per-message so high-volume VATSIM streams do not flood stdout. Use Kafka message timestamp age to detect real-time delay, processing duration to detect slow handlers, dropped stale messages to detect the existing 10s cutoff, and broker latest offsets for partition lag.
- ATC duplicating settings in `app/utils/server/vatsim/atc-duplicating.ts` use the V2 data shape: `description`, `authorCid`, `prefixes`, `suffixes`, optional `matchRegex`, and `mapping`. Prefer `prefixes`/`suffixes` for simple callsign families; keep `matchRegex` only for rules with numeric or otherwise constrained middle segments.
